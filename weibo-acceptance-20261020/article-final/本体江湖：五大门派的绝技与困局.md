# 本体江湖：五大门派的绝技与困局
- 作者：用户7448048573
- 发布时间：10-20 16:59
- 原文：https://weibo.com/7448048573/RnysjAME7
​​最近读到国家市场监督管理总局发布的 GB/T 48000.3—2026《本体建模要求》。看到标题时很兴奋——终于有国标级别的本体规范了。读完后发现，它面向的是标准化文件的语义建模，和我关注的企业业务本体是不同的问题。这让我想搞清楚一件事：2026 年，"本体"这个词在行业里到底指的是什么？各家巨头说的是同一个东西吗？于是有了这篇文章。

风起云涌

如何让 AI Agent 真正理解企业业务？

2026 年，这个问题把"本体"推到了企业 AI 的中心位置。Palantir、微软、SAP、Databricks 陆续推出以 Ontology 命名的产品能力；OpenAI、Google、Snowflake、IBM 也在解决相近的问题，却更多使用"语义层""上下文""知识目录"等表述。同期，中国发布了 GB/T 48000.3—2026《本体建模要求》。

巨头们面对的是同一道难题，差别在于它们选择从哪个环节、用什么机制解决企业语义问题。

图1：本体江湖，风起云涌。不同企业围绕“企业语义”，选择 Ontology、Semantic Layer、Context、Knowledge Catalog 等不同技术表述。

本文选取 10 家企业的产品能力和 1 项国家标准作为样本，将语义生命周期中反复出现的五种主导机制归纳为五大门派。分类单位是产品能力，不是整家公司——同一家公司的不同产品可以分属不同门派。

江湖之争

门派

在语义生命周期中的作用

门内绝技

显式建模派

形成：预先定义对象、关系与规则

固化为可编辑、可治理的持久模型

系统继承派

形成：继承业务应用语义

将 ERP 语义自动转为本体

痕迹归纳派

形成：从使用证据持续归纳

多源提取、权威排序、持续刷新

目录汇聚派

组织：汇聚元数据与治理信息

发现、血缘、质量与术语治理

任务组装派

使用：围绕任务组织上下文

按权限连接、检索与组装

第一派：显式建模派

重点案例：Palantir Ontology、Microsoft Fabric IQ Ontology / Salesforce Tableau Semantics

场景示例：库存低于阈值后，Agent 调用 Action Type“紧急调拨”，完成跨仓调拨、对象修改与 WMS 写回。

显式建模派先形成一套可查看、编辑和治理的持久语义模型，再把数据绑定到其中。模型不必从零手工创建，也可以从既有资产生成或对齐——判定依据是业务语义最终是否被固化为显式模型。

Palantir Ontology：把本体变成可执行的业务孪生

Palantir 将 Ontology 定义为"组织的数字孪生"。本体中的对象映射到真实业务实体，动作、函数和动态权限作为"动能元素"与语义元素纳入同一套模型。2026 年 7 月，Palantir 发布了适配多种主流 Agent SDK 的 Foundry Agent 模板，经过授权后，Agent 可以把本体中的对象类型、动作类型和查询函数作为 MCP 工具调用。

它的绝技是把对象、动作、权限和写回纳入同一个可执行模型，为打通从理解到执行的闭环提供了机制。代价是前期建模投入大，且语义资产与平台绑定较深。

Fabric IQ Ontology、Tableau Semantics：让一套定义跨应用复用

微软在 Ignite 2025 上推出 Fabric IQ，通过实体类型、关系类型、属性、动作和规则描述业务对象，再绑定到 OneLake 中的真实数据。Salesforce 的工程博客将统一本体建模列为 Agentforce 360 的关键架构维度，对外产品则使用 Semantic Data Model 和 Tableau Semantics 等表述。两者的绝技是让 BI、数据应用和 Agent 复用同一套定义，但语义统一的最后一公里仍然是组织治理——平台无法自动决定"谁有权定义客户"。

第二派：系统继承派

重点案例：SAP Datasphere

场景示例：S/4HANA 中沉淀的物料主数据和业务结构，被转换为物料、供应商、采购订单之间的可查询语义关系。

大量企业已经在 ERP 中沉淀了客户、物料、订单、合同和财务规则。系统继承派不从空白模型开始，而是把业务系统中已有的对象结构、元数据和业务上下文作为语义来源。

SAP Datasphere 可以根据已接入的数据及 SAP 应用中保留的业务上下文自动创建本体，用户再通过编辑器扩展和完善。

SAP HANA Cloud Knowledge Graph Engine 支持 RDF 和 SPARQL。SAP 还与 Palantir 建立了战略合作——SAP 提供业务数据本体，Palantir 提供运营决策能力，说明系统继承与显式建模可以出现在同一套架构中。这派的局限是：自动生成的质量高度依赖源系统的数据治理基础。

第三派：痕迹归纳派

重点案例：Databricks Genie Ontology、Snowflake Cortex Sense

场景示例：面对下单、支付和发货三种 GMV 口径，系统根据引用链路和来源权威等信号推荐首选定义。

痕迹归纳派把查询、仪表板、数据管道、文档和使用行为当作语义证据，让系统从企业日常留下的痕迹中持续归纳业务含义。

Databricks Genie Ontology：从使用行为中判断定义的权威性

处于公开预览阶段的 Genie Ontology 会从表、查询、仪表板、数据管道、文档和已连接应用中提取业务知识，并使用类似 PageRank 的机制评估不同定义的权威性。传统本体工程先找专家开会，再把业务知识写进模型；Databricks 反过来：先观察使用痕迹，再让系统持续生成和更新语义。从目前公开形态看，它更像一个持续更新的业务术语索引，而非传统意义上的知识模型。Databricks 内部基准测试显示，首次回答准确率从 text-to-SQL 的 52.4% 提升到 84.5%。

Snowflake Cortex Sense：从数据平台信号中持续刷新上下文

Cortex Sense 从历史查询、转换模型和 BI 指标等信号中建立并刷新上下文，仍处于私有预览阶段。Snowflake 表示，在其自身数据环境下，内部团队用一天建立了初始版本，内部测试准确率从 24.1% 提升到 86.3%。Snowflake-Labs 另外开源了 Ontology on Snowflake（显式建模），但这是社区项目，不是商业产品主线。

这派适合数据资产规模大、业务变化快的企业。但使用频率和来源权威只是治理信号，不等于业务共识——多个部门对同一概念存在冲突时，算法不能替代组织决策。

第四派：目录汇聚派

重点案例：Google Knowledge Catalog、IBM watsonx.data intelligence

场景示例：数据工程师搜索“客户流失率”，通过比较多个来源的血缘、质量和治理证据选择可信定义。

目录汇聚派不一定重新建设一套企业本体，而是先把散落在不同平台中的元数据、语义模型、业务术语、数据血缘、质量信息和治理规则汇聚起来，形成可发现、可追踪的知识入口。

Google Knowledge Catalog：用知识目录发现语义资产

Knowledge Catalog 聚合元数据、语义模型、业务术语和受治理定义，利用 Gemini 补充语义和映射关系。它同时支持 MCP 协议，Agent 可以通过语义搜索发现数据资产。

IBM watsonx.data intelligence：把业务定义与治理证据连在一起

watsonx.data intelligence 连接元数据、业务定义、数据血缘、数据质量和治理信息，为人和 AI 提供可信的业务上下文。本体在这里不是独立的核心概念，而是元数据治理工具箱中的一项能力。

这派的绝技，是把"在哪里、是什么意思、从哪里来、质量如何、谁能使用"放进同一个发现和治理入口。它能提高语义资产的可见性与可信度，却不能仅靠汇聚自动消除相互冲突的业务定义。

第五派：任务组装派

重点案例：OpenAI Frontier、Microsoft Foundry IQ

场景示例：销售 Agent 从 CRM、ERP 和邮件中获取相关信息，围绕客户询价任务组装完整上下文。

任务组装派优先解决任务上下文的连接、检索和组织，既可以直接组织原始信息，也可以消费前四派沉淀的语义模型和知识资产。

OpenAI Frontier：连接系统，提供共享业务上下文

Frontier 连接数据仓库、CRM、工单系统和内部应用，为 Agent 提供共享业务上下文，同时管理身份、权限和评测。OpenAI 自己的数据 Agent 用六层上下文覆盖 600PB 数据，但员工在区分同名数据表时仍然有困难——说明纯上下文连接仍有上限。

Microsoft Foundry IQ：把多类知识组织给 Agent

Fabric IQ 负责提供结构化、实时的业务运营上下文；Foundry IQ 则面向 Agent，从 Fabric IQ、Microsoft 365、应用和 Web 等来源组织并检索知识。Fabric IQ Ontology 属于显式建模，Foundry IQ 属于任务组装，两者的组合说明同一家公司的产品可以覆盖不同环节。

这派的优势是可以较快连接多个系统，适合业务变化快、难以预先完成全量建模的任务。但连接数据不等于理解业务。如果缺少稳定规则、统一口径和持久化语义资产，运行时组装也可能带来额外的一致性、推理和审计成本。

江湖之困

争的代价

当企业同时用了 SAP 的继承、Databricks 的归纳、Palantir 的建模和 OpenAI 的组装，四套语义体系之间怎么对齐？

企业更常见的麻烦，不是"没有本体"，而是同时拥有多套彼此不兼容的语义体系。

一家大型企业可能用 SAP 管理订单和物料，用 Salesforce 管理客户，用 Snowflake 或 Databricks 分析数据，再让多个 Agent 调用这些系统。同一个"客户"，在不同平台中可能对应不同定义：在 Salesforce 中侧重销售关系与联系人，在 SAP 中是结算主体或业务伙伴，在数据平台中又是经过清洗和指标加工后的分析对象。

这些定义未必有谁是错的，只是服务于不同业务目的。问题在于：它们之间缺少可复用的语义映射、来源记录和跨平台治理机制。

图3：孤岛没有消失，只是从数据库之间的记录隔离，升级为平台之间的定义、规则和权限隔离。

这和 2010 年代的"数据孤岛"问题如出一辙。当年每个部门各自建数据库，导致同一个客户在不同系统中有不同的记录。现在，不同平台各自维护本体、语义模型、知识目录和上下文配置，导致同一个业务概念被组织成彼此难以衔接的多套定义。

孤立的不只是数据，更是语义。

这个问题在 Agent 场景下尤其尖锐。想象一个采购 Agent 需要回答"供应商 A 的交付可靠性如何"——它需要从 SAP 中查询历史交付记录，从 Salesforce 中查询客诉记录，从 Databricks 中查询质量评分。

但三个系统中"供应商 A"的标识符不同、属性定义不同、质量评价口径不同。Agent 拿到三份数据，却无法判断它们说的是不是同一个供应商、同一批货、同一个时间口径。没有跨平台的语义映射，Agent 只是在汇总三份互不关联的报告，而非在做一次有意义的判断。

当 Agent 的能力从"回答问题"升级到"执行操作"时，这个问题会更加严重。一个 Agent 如果基于错误的语义对齐做出了采购决策并写回了 ERP，造成的损失不是一份错误报告，而是一笔真实的财务损失。

语义孤岛的代价，会随着 Agent 自主权的提升而显著放大。

局中人出不去

数据可以跨系统流动，但语义不能。

数据背后的业务含义、指标口径、规则、权限和动作定义，往往仍保存在平台特定的模型与接口中。无论语义资产由显式建模、系统继承或痕迹归纳形成，还是在目录汇聚与任务组装中被重新索引和封装，只要缺少可交换的表示和跨平台映射机制，就可能形成新的语义锁定。

C3.ai 推出了一个"基于 Palantir 的生成式 AI"模块——它不替代 Palantir，而是在 Palantir 之上叠加一个自然语言层，同时通过自己的 Type System 跨系统连接 SAP、Salesforce 和 Snowflake，试图用一个统一的抽象层打通多个平台的语义。

但它并没有从根本上解决问题：C3.ai 的 Type System 本身也是私有格式。

用一把新锁替代三把旧锁，管理成本降低了，锁定本质没有变。

这是局中人的结构性困境：每个平台都有动力建自己的语义层，但没有动力让自己的语义资产被其他平台复用。 打通语义孤岛的收益由全行业共享，但成本由率先开放的一方承担。这不是技术问题，而是商业博弈。

更深层的矛盾在于：语义层越强大、越深度集成到平台中，迁移成本就越高。Palantir 的 Action Types 可以写回 ERP，这是巨大的能力——但也意味着你的业务操作逻辑被编码到了 Palantir 的本体中，离开 Palantir 就意味着重建这些操作定义。

能力越强，锁定越深。

局外人进不来

开放标准的本体互操作不是一个新话题。W3C OWL 2 定义了"本体怎么写"，ISO/IEC 21838 标准化了 Basic Formal Ontology（BFO）作为顶层本体框架并被美国国防部采纳为基线标准，ISO 23726 的工业数据本体（IDO）也将于2026年正式发布，中国的 GB/T 48000.3 则为标准化文件建立了领域本体规范。

从语言层到顶层哲学层到部分工业领域，开放标准体系已经相当成熟。

但文章中讨论的主要商业产品——Palantir、微软、Databricks、C3.ai——没有一个将 OWL 作为核心架构。 SAP 的 HANA Cloud Knowledge Graph Engine 支持 RDF 和 SPARQL 查询接口，是少数例外之一，但其本体的核心生成和管理同样不依赖 OWL。标准界在 OWL 体系内，商业界在 OWL 体系外，两个世界交集很少。

这不是因为商业公司不懂标准，而是因为 OWL 的设计初衷和企业 AI Agent 的需求之间存在错位。

OWL 擅长形式化推理——它可以表达"实施日期应晚于发布日期""规范性要素与资料性要素互斥"这类逻辑约束，推理引擎可以自动验证一致性。

但企业 AI Agent 最紧迫的需求是另一类："当库存低于阈值时自动触发采购订单并写回 ERP""从 50 个数据源中实时提取业务术语并按权威性排序""让 Agent 在毫秒级延迟下通过 MCP 调用本体中的操作"。

局外人有规矩，但规矩是为另一个问题设计的。

OWL 诞生于2004年的语义 Web 运动，目标是让互联网上的数据可以被机器理解和推理。二十年后，企业 AI 的核心场景已经从"跨网站的数据互联"变成了"跨平台的 Agent 协作"。规矩还在，但局已经换了。

从 BFO 这样的顶层哲学分类，到"客户""订单""产品"这样的企业业务概念之间，仍然缺少可复用的中间层标准。Palantir、微软、SAP、Databricks 各自用私有格式填补的，正是这个中间层。

开放标准走到了门口，但还没有进入企业业务的房间。

思考与破局

Agentic AI 暴露了企业 AI 的一个关键缺口：Agent 能够访问数据，不代表它真正理解业务。

五大门派并不是五选一，多数企业最终会采用混合架构。而这场分裂中最大的结构性风险，不是选择哪一种语义形成或供给机制，而是不同平台之间的语义模型、定义和规则能否被识别、映射和迁移。

破局需要的可能不是"让大家都回到 OWL"，而是找到一种新的互操作机制——既有开放标准的可交换性，又有商业产品的性能和易用性。

MCP 协议（已被 Palantir、Google、Anthropic 等采纳）可能是一个方向，但它目前解决的是工具调用的互操作，而非语义模型本身的互操作。语义模型的互操作需要回答更难的问题：怎么让 Palantir 的 Object Type、微软的 Entity Type、SAP 的自动生成本体和 Databricks 的术语索引之间，建立可机器读取的映射关系？

OWL 标准体系走到了工业领域的门口，但还没有进入企业业务的房间。商业产品走进了房间，但各自锁上了门。

下一步的突破，也许不在于某一个门派的绝技更强，而在于找到一种让所有房间的门都能打开的钥匙。

真正的一统江湖，不是让所有企业使用同一种本体语言，而是让不同语义体系的模型、定义和规则能够被识别、映射和互操作——无论它们是用 OWL、JSON、属性图还是私有格式表达的。
